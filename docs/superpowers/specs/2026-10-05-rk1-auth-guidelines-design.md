# Гайдлайны РК1: аутентификация, сессия и доступ к данным

Дата: 2026-10-05. Статус: на ревью.

## 1. Цель

Публичный репозиторий `TP-Prepare/technopark-guidelines` с ожиданиями преподавателей Технопарка (2-й семестр, курс по веб-разработке VK Education) к рубежным контролям командного проекта. Первая папка — `rk1/`.

РК1 про безопасность: каждый студент команды (2 фронта и 2 бэка) понимает, как устроены аутентификация, сессия и авторизация доступа к данным в его проекте, и может это показать в коде, DevTools и `curl`.

Технические требования РК1, к которым привязан документ:

1. Авторизация с валидацией.
2. Регистрация с валидацией.
3. Страница файла, создание блоков в файле.
4. Список файлов пользователя.

Пункты 1–2 покрываются разделами про пароли, сессию, CORS и CSRF; пункты 3–4 — разделом про доступ к данным (владение ресурсами, IDOR).

### Успех

- Команда по `rk1/README.md` понимает, что обязательно, выбирает вариант A, B или C и знает, что читать дальше.
- Ментор проводит РК по `checklist.md` и `questions.md`, не придумывая проверки сам.
- Текст общий для всех команд: нет названий команд и кода конкретных проектов; примеры на `example.ru`, `api.example.ru`, `avatars.example.ru`, `evil.example`.

## 2. Читатели

- **Студенты** — объяснение архитектуры, требования, самопроверка, подготовка к вопросам.
- **Менторы и преподаватели** — чек-лист приёмки и вопросы с критериями ответа.

Обе аудитории видят все файлы. Критерии ответов спрятаны под `<details>`, чтобы вопросы читались без подсказки.

## 3. Политика требований

### 3.1. Обязательный минимум (любой вариант)

Невыполнение любого пункта — РК не сдан.

1. Пароли хешируются bcrypt или argon2id, не логируются, длина пароля ограничена.
2. Ответ на неудачный вход не раскрывает, существует ли логин.
3. Все входные данные валидируются на сервере; клиентская валидация — только UX.
4. Токенов и `session_id` нет в `localStorage`, `sessionStorage` и в cookie без `HttpOnly`.
5. Cookie с refresh-токеном или сессией: `HttpOnly`, `Secure` на проде, `SameSite=Lax` или `Strict`, узкий `Path`, где применимо.
6. Logout завершает сессию на сервере, а не только чистит cookie.
7. Access-токен живёт не больше 15 минут (A, B); у сессии есть срок жизни (C).
8. CORS: точный белый список origin, без `*` вместе с credentials; preflight отвечает до авторизации.
9. Варианты A и C: CSRF-защита на изменяющих методах по §3.3, отказ — 403.
10. Каждая ручка с ресурсом проверяет владельца на бэке.
11. На проде HTTPS; секреты (ключи JWT, CSRF) в переменных окружения, не в репозитории.

### 3.2. Варианты реализации сессии

Принимаются три варианта. Команда выбирает один и на защите объясняет компромиссы.

| | A (рекомендуемый) | B (допустимый) | C (допустимый) |
|---|---|---|---|
| Схема | access и refresh в HttpOnly-cookie + CSRF | access (Bearer) в памяти JS + refresh в HttpOnly-cookie | `session_id` в HttpOnly-cookie, сессии в Redis/БД + CSRF |
| Что получает XSS | действия от имени пользователя, пока вкладка открыта; токен унести нельзя | то же + может унести access-токен и пользоваться им до истечения | как в A |
| CSRF | нужен | только для refresh-cookie; закрыт `Path` и `SameSite` | нужен |
| Отзыв | refresh — сразу; access — по истечении TTL | как в A | сразу |
| Работа фронта | `credentials: 'include'`, CSRF-заголовок, повтор после 401 | хранить токен в памяти, ставить `Authorization`, повтор после 401 | `credentials: 'include'`, CSRF-заголовок |

`variant-b.md` прямо отвечает на вопрос «почему не хранить access в памяти»: это не утечка сама по себе, но при XSS токен можно унести и использовать вне вкладки до конца TTL; HttpOnly-cookie это исключает ценой обязательной CSRF-защиты.

Токены в `localStorage` — не вариант, а нарушение минимума (§3.1 п. 4); разбирается в `basics.md` и `pitfalls.md`.

### 3.3. CSRF: минимум и усиление

**Минимум** — Double Submit Cookie:

- токен генерирует сервер криптостойким генератором, не меньше 128 бит;
- CSRF-cookie без `HttpOnly`; фронт отправляет её значение в заголовке `X-CSRF-Token`;
- проверка на POST, PUT, PATCH, DELETE; отказ — 403 (не 401: на 401 фронт делает refresh и повторяет запрос);
- GET не меняет данные;
- авторизационные cookie с `SameSite=Lax` или `Strict`.

**Настойчиво рекомендуется** (ожидается для хорошей оценки):

| Опция | Что закрывает |
|---|---|
| Префикс `__Host-` у CSRF-cookie (`Secure`, `Path=/`, без `Domain`) | поддомен не может поставить или перезаписать cookie (cookie tossing) |
| Проверка `Origin` / `Sec-Fetch-Site` на login, register, refresh | login CSRF: вход жертвы в аккаунт злоумышленника |
| Только `Content-Type: application/json` на изменяющих ручках | форма и `text/plain` отклоняются; JSON требует preflight, который CORS не пропустит с чужого origin |
| Сравнение за постоянное время (`hmac.Equal`, `subtle.ConstantTimeCompare`) | подбор токена по времени ответа |

**По желанию:**

| Опция | Что закрывает |
|---|---|
| Подпись токена HMAC с привязкой к пользователю или сессии | подложенный с поддомена честно выданный токен чужого аккаунта не проходит |
| Проверка `Origin` / `Sec-Fetch-Site` на всех изменяющих запросах | второй слой до проверки токена |
| Новый CSRF-токен при login, refresh, logout | token fixation между пользователями |
| `SameSite=Strict` у авторизационных cookie | переходы с чужих сайтов приходят без cookie; SPA не ломает, если HTML не требует авторизации |
| Нет пользовательского HTML/SVG на поддоменах (`Content-Type` загрузок, CSP) | источник атак с того же сайта |

Оговорка в тексте: `__Host-` требует `Path=/`, поэтому для refresh-cookie с узким `Path` подходит только `__Secure-`.

Synchronizer Token в гайдлайне не описывается.

Как опции переводятся в баллы, документ не определяет — решает ментор.

## 5. Содержание документов

### 5.1. `README.md` (корень)

Что это и для кого, список рубежей (пока только РК1), как читать, как предложить правку (issue или PR, студенты тоже могут).

### 5.2. `rk1/README.md`

- Требования РК1 (4 пункта из §1) и тезис «РК1 про безопасность».
- Обязательный минимум §3.1.
- Таблица сравнения вариантов §3.2 и правило выбора.
- Маршрут чтения: студент — `basics` → `cors` → свой вариант → `csrf` (A, C) → `access-control` → `pitfalls` → `checklist` и `questions`; ментор — `checklist` и `questions`.

### 5.3. `rk1/basics.md`

- Идентификация, аутентификация, авторизация.
- Модель угроз: XSS, CSRF, кража токена, IDOR, перебор паролей.
- Флаги cookie: `HttpOnly`, `Secure`, `SameSite`, `Path`, `Domain`, префиксы `__Host-` и `__Secure-`.
- Site и origin: что одно и то же для `SameSite`, а что для CORS. Картинка `site-vs-origin.png`.
- Где можно хранить токен: память, `localStorage`, cookie — и что видит XSS в каждом случае.
- JWT: подпись не шифрует; stateless и stateful; зачем пара access и refresh.
- Хеширование паролей.

### 5.4. `rk1/cors.md`

- Same-origin policy: браузер отправляет запрос, но не отдаёт ответ JS без разрешения сервера.
- Простые запросы и запросы с preflight; что запускает `OPTIONS` (методы кроме GET/HEAD/POST, `Content-Type: application/json`, свои заголовки `Authorization`, `X-CSRF-Token`).
- Заголовки: `Access-Control-Request-Method/-Headers` в запросе; `Allow-Origin`, `Allow-Methods`, `Allow-Headers`, `Allow-Credentials`, `Max-Age`, `Vary: Origin` в ответе.
- Preflight отвечает `204` до авторизации; `OPTIONS` не должен попадать в auth-middleware.
- Credentials: точный origin, не `*`; `credentials: 'include'` на фронте.
- `Expose-Headers` (вариант B: без `Authorization` JS не прочитает токен).
- CORS не защищает от CSRF: простые запросы уходят без preflight, запрет касается только чтения ответа.
- Когда CORS не нужен: один origin на проде через прокси, proxy в Vite при разработке.
- Mermaid: preflight → запрос; preflight отклонён.

### 5.5. `rk1/variant-{a,b,c}.md`

Один шаблон:

1. Схема одним абзацем + eraser-картинка `variant-{a,b,c}.png`.
2. Таблица cookie: имя, флаги, `Path`, срок жизни.
3. Потоки Mermaid: вход/регистрация; обычный запрос; истёк access → refresh → повтор (A, B) или истекла сессия (C); перезагрузка страницы (A, B); выход.
4. Что делает бэк, что делает фронт.
5. Что может XSS и что может CSRF в этом варианте, чем закрыто.
6. Плюсы и минусы.

Особенности:

- **A** — access `Path=/api/…`, refresh с узким `Path` на ручки продления, CSRF по `csrf.md`.
- **B** — access в замыкании или модуле клиента, не в сторе с persist; `Expose-Headers: Authorization`; почему вариант допустим, но не рекомендуется (§3.2).
- **C** — сессии в Redis или БД, мгновенный отзыв, обращение к хранилищу на каждый запрос, «выйти со всех устройств».

### 5.6. `rk1/csrf.md`

- Что такое CSRF: браузер сам прикладывает cookie.
- Когда актуален: A и C; в B — только refresh-cookie.
- `SameSite` и почему его мало: поддомены с пользовательским контентом, cookie tossing, GET с побочными эффектами, старые браузеры.
- CSRF и XSS: XSS на основном origin не закрывает никакая CSRF-защита; XSS на соседнем поддомене при cookie-авторизации превращается в действия в основном приложении — это и отсекают `Origin` и `__Host-`.
- Double Submit: минимум, настойчиво рекомендуемое и по желанию — по §3.3.
- Login CSRF.
- 403, а не 401.
- Mermaid: атака без защиты; отказ при Double Submit; cookie tossing и как его останавливают `__Host-` и подпись.

### 5.7. `rk1/access-control.md`

- Аутентификация не равна авторизации доступа к ресурсу.
- IDOR на примере `GET /files/{id}`.
- Вложенные ресурсы: блок принадлежит файлу, файл — пользователю; проверка по всей цепочке.
- Список строго по `user_id` из сессии, не из параметра запроса.
- `user_id` из тела запроса игнорируется (mass assignment).
- 404 на чужой ресурс, чтобы не раскрывать существование.
- Серверная валидация входных данных.
- Mermaid: запрос к чужому `id` → 404.

### 5.8. `rk1/checklist.md`

- В начале: ментору подготовить двух тестовых пользователей.
- Пункт = уровень (**[минимум]**, **[рекомендуется]**, **[по желанию]**) + что проверить + как (код, DevTools, готовая команда `curl`) + ожидаемый результат.
- Группы: пароли и регистрация; сессия своего варианта (флаги в Application, нет токенов в `localStorage`, после logout старый refresh или `session_id` даёт 401); CORS и preflight (`curl -X OPTIONS` с разрешённым и чужим `Origin`); CSRF для A и C (без `X-CSRF-Token` → 403, с ним проходит, GET без токена проходит); доступ к данным (чужой `id` → 404, список только свой, `user_id` в теле игнорируется).

### 5.9. `rk1/questions.md`

- 25–30 вопросов, сгруппированных по разделам `basics`, `cors`, `csrf`, `access-control`, вариантам.
- Два вида: на понимание и «покажи в своём коде».
- Под каждым — `<details>` с критериями засчитывания и типичными неверными ответами.
- Каждый студент отвечает про весь поток авторизации, фронт и бэк; «покажи в коде» — по своей роли.
- Число вопросов и баллы определяет ментор.

### 5.10. `rk1/pitfalls.md`

Запись: симптом → причина → как проверить → как исправить. Минимальный набор:

- JWT не видно в Application (вариант B — его там и не должно быть).
- `Path` прячет cookie из DevTools (не прячет).
- Нет CORS-заголовков в `curl` (запрос без `Origin`).
- Preflight получает 401 (`OPTIONS` попал в auth-middleware).
- `Allow-Origin: *` вместе с credentials.
- Бесконечный refresh (CSRF-отказ кодом 401 вместо 403).
- `localhost` в белом списке прода.
- Токен в `localStorage` ради переживания F5 (для этого есть refresh-cookie).

### 5.11. Источники

В конце каждого файла — раздел «Источники»: MDN, OWASP CSRF Prevention Cheat Sheet, OWASP Authentication и Password Storage Cheat Sheets, RFC 6265bis (cookie, `SameSite`, префиксы), спецификация Fetch (CORS). Утверждения о поведении браузера не расходятся с источником.

### 6.3. Цветовая конвенция eraser

Зоны (верхние группы):

| Зона | `color` |
|---|---|
| Браузер пользователя | `blue` |
| Наш бэкенд: API, БД, Redis | `green` |
| Злоумышленник: чужой сайт, внедрённый скрипт | `red` |

Вложенные группы «JS-контекст страницы» и «Хранилище cookie» — цвет родителя и `"styleMode": "plain"`.

Тип стрелки — по зоне источника (через `containerId` до верхней группы):

| Источник | `color` | `lineStyle` | Легенда |
|---|---|---|---|
| узел в зоне злоумышленника | `red` | `dotted` | Атака |
| узел в группе «Хранилище cookie» | `orange` | `solid` | Браузер прикладывает сам |
| узел в группе «JS-контекст страницы» | `black` | `dashed` | Делает код фронта |
| остальное | не задавать | не задавать | Прочие связи |

Правило определения группы — по фиксированным `id` групп: `attacker`, `cookie-jar`, `js-context`. Легенда — ровно одна (`"id": "legend"`, `"width": 340`), только зоны и типы стрелок, присутствующие на схеме; `bun run check` печатает ожидаемые `entries`.

Сайт-схема `site-vs-origin` использует те же зоны: `example.ru` и поддомены — `green` (наш), `evil.example` — `red`.
